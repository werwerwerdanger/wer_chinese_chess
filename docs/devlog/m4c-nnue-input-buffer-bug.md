# m4c — NNUE 评估输入缓冲区不清零（"AI 怎么那么笨"的真凶）

> 2026-10-04 发现并修复。这是继 `m4b`（搜索视角 bug）之后更脏的一个 bug：
> **模型本身没问题，是喂给它的输入向量被污染了。**

## 症状

修完 m4b（奇数深度挑最差着法）后，AI 还是"笨"：开局第一手走 **炮八进七**——
把炮送到对方底线上，被车吃回，净亏一个炮的兑换，而引擎自己给这步的评分是 −544。

`tools/distill/showplay.mjs`（新写的自对弈打印器）一眼看出问题：

```
#  1 红 炮八进七  | 搜索 -544(红方视角) | 静态 -1754
#  2 黑 车9进1    | 搜索 -6103            | 静态 -145
#  3 红 炮八平六  | 搜索 -5845            | 静态 +1886
...
#  5 红 车一平二  | 搜索 -6103            | 静态 -6103   ← 之后一路钉在 -6103（饱和）
```

开局静态分应该是 **+83**，这里却是 **−1754**；紧接着还有 +1886、−2177 这种乱跳，
最后稳定在 −6103（≈ atanh 饱和上限 6145）。而 `probe-eval.mjs` 用**同一个模型**评同一个
局面是 +83.4。**同一个模型、同一个 FEN、两个脚本结果不同** → 一定是调用方式的问题。

## 定位

`engine-ai/src/nnue.ts`：

```ts
evalBoard(board: Board): number {
  const key = board.hashKey;
  ...
  encodeFenInto(board.toFen(), this.input);   // ← this.input 是跨调用复用的 SAB 视图
```

而 `encodeFenInto` 只写 1、**从不写 0**：

```ts
out[(r * 9 + c) * 14 + pi] = 1;   // 占位棋子置 1
out[VEC_LEN - 1] = ...;           // 行棋方
```

于是新局面的向量 = **当前局面 ∪ 之前评估过的所有局面**（棋子只增不减）。
`probe-eval.mjs` 每次 `new Float32Array(...)` 所以干净，`showplay` 走 `evalBoard` 就被污染。

## 判别实验（可直接复现）

同一 FEN、同一模型、两种调用方式：

| 调用方式 | B 局面的评估 |
|---|---:|
| 独立实例（buffer 干净） | **−411.5** |
| 先评过 A 再评 B（复用 buffer） | **−76.3** ← 实际是"A 的全部棋子 + 黑方走"那个局面的分 |

−76.3 恰好等于"完整开局、黑走"的真实分数——证明残留的是 A 的棋子，
只剩"并集"这一种解释。**100% 确认。**

另外两个侧面证据：
- 红多一车局面：红走 +621 / 黑走 +632（都是强正）→ **模型方向没反**，
  "蒸馏反了"这个猜测被排除；labels（`label.mjs` 已把 UCI 行棋方视角转成红方视角）也是对的。
- 搜索里第一次评估是对的，后面全错 → 解释了过去所有怪现象：
  评分 ±6103 饱和、20 局里 19 盘和棋、63 代迭代"没有提升"。

## 修复

```ts
export function encodeFenInto(fen: string, out: Float32Array): void {
  out.fill(0);                     // 复用 buffer 必须先清零（1261 个 float，代价可忽略）
  ...
}
```

放在 `encodeFenInto` 里而不是 `evalBoard` 里：这样任何复用 buffer 的调用方都安全。
`encodeFen`（新建数组）多一次填零，成本可忽略。

## 验证

1. 回归测试 `engine-ai/tests/nnue.test.ts`：
   "评估结果与评估历史无关" —— 同一个 evaluator 里 A→B，与干净实例单独评 B 必须一致。
   **去掉 `out.fill(0)` 跑 → 1 fail；加回 → 3/3 pass。**
2. 端到端（`showplay.mjs --plies 12 --depth 3`）：

```
#  1 红 炮八平五  | 搜索 +88(红方视角) | 静态 +83
#  2 黑 炮8平5    | 搜索 +38             | 静态 +54
#  3 红 马八进七  | 搜索 +57             | 静态 +88
#  4 黑 马8进7    | 搜索 +54             | 静态 +38
#  5 红 车九平八  | 搜索 +27             | 静态 +57
```
   中炮、屏风马、车巡河——是正经棋了，评分离散度也从 ±6103 收到 ±100 量级。
   `POST /think` 开局返回 `b2e2`（炮八平五）+87.6（修复前是 `b2b9` −544）。

## 顺带做的两件事

1. **NNUE 吞吐基准** `tools/distill/bench-eval.mjs`：1500 个不同局面 → **0.394 ms/次 ≈ 2500 次/秒**。
   试过 `intraOpNumThreads:1 + executionMode:'sequential'`（想省线程调度开销）→ 反而 **0.501 ms/次**，
   已回退成 ORT 默认。**结论要测，别猜。**
   3s 思考 ≈ 7k 次评估 → 开局只能搜到深度 2~3，这才是当前棋力天花板；
   要再上一个台阶得让评估更快（onnxruntime-web + WASM SIMD 方案 A）或换更小的网。
2. `nnue-serve` 的深度钳制从 `≤3` 放宽到 `≤6`：反正时间先卡住，残局分支少时能多搜几层。

## 教训

1. **复用缓冲区是热路径优化的常规手段，但"只写 1 不写 0"是个隐形杀手**；
   凡是"填充稀疏 one-hot"的函数，第一件事就是清零，并写进注释/测试。
2. **同一模型两个脚本结果不一致时，先怀疑喂进去的数据，别怀疑模型**——
   这次正是 `probe-eval`（干净）与 `showplay`（污染）的对照把 bug 钉死的。
3. 新工具 `showplay.mjs` 的价值：把"AI 很笨"这种模糊抱怨，变成"第 1 手就走炮八进七、静态分 −1754"
   这种可执行的事实。**排障第一步永远是先看它实际在下什么。**
4. 本 bug 与 m4b 叠加：m4b 让奇数深度挑最差着法，m4c 让评估值整体失真。
   两个都修掉之前，任何"模型棋力"的测量（包括 63 代迭代的 Gate）都不可信，需要重测。
