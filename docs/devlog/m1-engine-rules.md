# M1 引擎规则层 开发日志

## 2026-09-12 11:00 ~ 11:30

### 做了什么
从零实现 TS 引擎规则层，5 个模块：types.ts（棋子编码）、constants.ts（坐标系/Zobrist 表）、board.ts（棋盘/FEN/make-unmake）、movegen.ts（七子走子生成）、legality.ts（将军检测/合法过滤）。

### 设计决策
1. **90 格一维数组**（row*9+col）而非 9×10 二维——缓存友好，索引一次乘加
2. **Piece 编码**：bit3 存颜色，低 3 位存种类。红子 0-7、黑子 8-15
3. **Zobrist 增量哈希**：make/unmake 时只 XOR 变化的位，不重算全盘。M3 置换表直接复用
4. **将位缓存**：kingSquare[2] 实时维护，inCheck 从将位反向探测（车/炮/马/兵四类攻击线），不做全盘攻击图
5. **vitest 单测**：18 用例 + perft 金标准

### 踩坑记录（>>报告素材："遇到的问题与挑战"）

**坑1：Piece.None=0 与 RedKing=0 编码冲突**
- 现象：18 个测试挂了 17 个，全是"非法字符 K in FEN"——初始局面都加载不了
- 根因：红帅编码 0 和空格编码 0 相同，`squares[i] === Piece.None` 把红帅当空格
- 修复：None 改 255，判断空格的地方全要 `!== 255`
- 教训：**枚举设计第一天就要检查"零值冲突"**，特别是"无/空"这类哨兵值

**坑2：colorOf 位运算错误**
- 现象：perft(1) = 42，期望 44；分棋子统计发现炮走子少 2 个
- 诊断：写了诊断测试逐棋子打印走子数，红炮纵向"隔山吃马"的两步没生成
- 根因：`colorOf = p & 8` 返回 8，但 `Color.Black = 1`，`8 === 1` 为 false → 所有吃黑子的走子被过滤
- 修复：`colorOf = (p >> 3) & 1`
- 教训：位标志和枚举值混用时，移位归一化不能省

**坑3：inPalace 负数行越界**
- 现象：黑方伪合法走子 47 个（期望 44）；makeMove 时 Zobrist 数组下标 -6 崩溃
- 根因：黑方九宫判定 `row <= 2`，row=-1 也通过 → 黑将/士能"走出棋盘上方"
- 修复：inPalace 加 `row < 0 || row > 9` 边界检查
- 教训：**方向性判断（上/下）必须显式查两边边界**，JS 负数索引不报错但访问到错误内存（Uint8Array 负索引是 undefined）

**坑4：vitest 下 const enum 跨文件失效**
- 现象：改成普通 enum 前测试全挂，`Piece.RedKing` 是 undefined
- 根因：esbuild 逐文件转译，不做 const enum 的跨文件内联（tsc 全量编译才有）
- 修复：全项目禁用 const enum，只用普通 enum
- 教训：构建工具链的行为差异要在第一天用最小 demo 验证

### 测试结果（>>报告素材："运行调试"）
```

perft(1) = 44        ✓ 精确
perft(2) = 1920      ✓ 精确
perft(3) = 79666     ✓ 精确
perft(4) = 3290240   ✓ 精确（约 7 秒）
```
perft 是走子生成器正确性的金标准：数 depth 层走子树叶子数，与公认参考值全等说明所有规则（蹩马腿/塞象眼/炮架/过河兵/将帅照面/送将过滤）实现无误。

另：测试用例自己也写错过 3 次（FEN 坐标算错、用了非 FEN 字符 'e'、行宽 8≠9），靠"分棋子统计 + 单走子生成"两招定位。**引擎对、测试错**的情况提醒我们：断言失败先复查期望值本身。
